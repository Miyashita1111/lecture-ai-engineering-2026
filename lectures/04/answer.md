### 基礎：判定の順序（理由→判定／判定→理由）を入れ替える

- やったこと：
  - `app/judge.py` に `--verdict-first` を追加した。`CriterionVerdict`（reason→verdict）と同じ中身でフィールドの順だけを入れ替えた `CriterionVerdictFirst`（verdict→reason）を作り、出力の型と「# 出力の形式」の指示文の両方を判定→理由の順にそろえた。既定（演習）の動きは変えていない
  - 型だけ入れ替えて指示文が「理由を先に」のままだと、2つの指示が食い違って何を比べているか分からなくなるので、両方を変えて「1つの変更」とした
  - スキーマ上の順序が入れ替わっていることと、偽モデル（`--model test`）で集計まで通ることをテストした（`uv run pytest -q` → 25 passed）
  - 同じ `labels.jsonl`・同じ `rubric.md`（STEP 3 で直す前）・同じモデルで、順序だけを変えて採点した

```bash
uv run python -m app.judge --out lectures/04/judge_result_reason_first.json
uv run python -m app.judge --verdict-first --out lectures/04/judge_result_verdict_first.json
```

- 結果（gemini-3.5-flash-lite、temperature=0、各 1 回）：

| 基準 | 理由→判定（既定） | 判定→理由（指示が食い違ったまま） | 判定→理由（食い違いを直した） |
|---|---|---|---|
| 根拠 | 6/9（要確認 1） | 8/10 | 6/9（要確認 1） |
| 範囲 | 10/10 | 10/10 | 10/10 |
| ヒント | 9/10 | 9/10 | 9/10 |
| 分かりやすさ | 7/10 | 8/10 | 8/10 |
| 回の表示（コード） | 7/10 | 7/10 | 7/10 |
| 総合 / coverage | 6/9 / 90% | 7/10 / 100% | 6/9 / 90% |
| 要確認の件数 | 1（#05 根拠） | 0 | 1（#05 根拠） |
| 不一致の件数 | 10 | 8 | 9 |

  - **最初の判定→理由の実行は、比較として正しくなかった。** 出力の型と「# 出力の形式」は判定→理由にしたが、`rubric.md` の「採点のしかた」に「先に理由を書いてから判定を決める」が残っていて、モデルに食い違う指示が渡っていた。この実行では要確認が 0 件になり（#05 を unsure にせず pass にした）、#06 の根拠も pass になって、一致率は見かけ上いちばん高かった
  - `--verdict-first` で rubric の該当文も入れ替えるよう直して再実行すると、根拠・要確認・coverage は理由→判定と**まったく同じ**に戻った。違いは #08 の分かりやすさ 1 件だけ（理由→判定は pass、判定→理由は fail）
  - #08 の分かりやすさは、自分も fail にしていたので一致率は上がった（7/10 → 8/10）。しかしこれは、役割放棄（範囲の問題）を分かりやすさに持ち込んだ**同じ混同で一致しただけ**で、講師のラベルは pass。判定→理由の方が、基準を独立に見られなくなったと読める

- 気づき・疑問：
  - 順序そのものの影響は小さく（10 件中 1 項目）、**指示の食い違いの影響の方がずっと大きかった**。食い違いがあると、モデルは unsure（決めていない論点）を出さずに pass/fail を決めてしまい、要確認が消えて coverage が 100% になった。「一致率が上がった・coverage が上がった」を改善と読むと、むしろ人が見るべき項目を見落とすことになる
  - 一致率は「人のラベルが正しい」前提の数字なので、人と LLM が同じ間違いをすると上がる。#08 の分かりやすさがその例。一致率だけでなく、不一致・一致した項目の理由まで読まないと判断を誤る
  - 理由→判定でも混同は起きた（#06 根拠：宿題の答えを書いたことを根拠の fail にした）。順序を変えるだけでは混同は防げない
  - 疑問：temperature=0 でも同じ設定の 2 回で結果が完全に一致する保証はない。1 回ずつの比較で「1 項目の差」を順序の効果と言ってよいのか。複数回実行して揺れの幅を見る必要がある

### 発展：GPQA Diamond を調べる

- データセット：GPQA（Graduate-Level Google-Proof Q&A Benchmark）の Diamond サブセット
  - 論文：Rein et al., "GPQA: A Graduate-Level Google-Proof Q&A Benchmark"（arXiv:2311.12022, https://arxiv.org/abs/2311.12022）
  - データ：https://huggingface.co/datasets/Idavidrein/gpqa （利用規約への同意が必要）
- 中身：生物学・物理学・化学の大学院レベルの4択問題。全体（extended）546問は物理 227・化学 214・生物 105 問で、有機化学（144）、量子力学（64）、分子生物学（85）などが多い。Diamond はそのうち 198 問
- 読んだ問題の要約（全文は貼らない。著者が学習データへの混入を避けるため、問題をそのままネットに載せないよう求めているため）：
  - 問題1（物理・量子力学）：寿命の違う2つの量子状態を、はっきり区別して観測するのに必要なエネルギー差を4択から選ぶ。エネルギーと時間の不確定性関係から、寿命をエネルギー幅に直して比べる
    - 自分なら：解けなかった。公式を知っていれば計算は1行だが、「寿命→エネルギー幅に直して比べる」という発想が出てこない
    - LLM にとって：公式の当てはめと桁の比較なので、比較的やさしいと思う
    - 気づいたこと：データの解説（Explanation）に、寿命の値の書き間違いと思われる箇所があった（片方の寿命を 10⁻¹¹ s と書いているが、計算結果はもう一方の寿命の値に対応している）。専門家2人が検証したデータでも、解説の細部までは誤りが残る
  - 問題2（物理・原子核）：原子核の多体計算でよく使う「インパルス近似」（核の中の核子を自由な核子のように扱う近似）が、4つの仮定のうちどの組み合わせから導かれるかを選ぶ
    - 自分なら：解けない。計算ではなく、近似の前提を正確に知っているかを問う問題で、検索してもすぐには分からない
    - LLM にとって：専門的な知識を正確に覚えているかで決まる。もっともらしい仮定（クォークが非相対論的、など）を混ぜてあり、雰囲気で選ぶと間違える
  - 問題3（化学・有機）：アルケンを持つアリールエーテルを HBr と反応させたら、TLC で原料のスポットが減り、新しいスポットが2つ出た。生成物の構造として正しい組み合わせを選ぶ
    - 自分なら：解けそう。HBr の付加でカルボカチオンができ、その後の反応で2種類の生成物ができる、という流れを順に追えば絞れる
    - LLM にとって：化合物名から構造を頭の中で組み立て、反応の経路を何段階も追う必要がある。TLC の観察（スポットが2つ）という実験の文脈を、化学の推論に結びつけるところも難しい
- 作った人と手順：
  - 作問：Upwork で集めた **61 人**の契約者。その分野で博士号を持つか博士課程に在籍している人
  - 検証の流れ（1問ごと）：作問者が問題・選択肢・解説を書く → **同じ分野の専門家1人目**が解いてフィードバック → 作問者が修正 → **同じ分野の専門家2人目**が解く → **別分野の非専門家3人**が、Web 検索あり（LLM は禁止）・最低15分（平均37分）で解く
  - 報酬で質を誘導している：作問者は「専門家が正解するほど」「非専門家が間違えるほど」報酬が増える（専門家にとって明確で、検索では解けない問題を作る動機になる）
  - Diamond の選び方：専門家が2人とも正解（2人目が間違えた場合は、間違いを明確に説明できたものに限る）、かつ非専門家3人のうち正解が1人以下の問題だけを残す。収集した 564 問から 198 問まで絞っている
  - 正答率：専門家 81.3%、非専門家 22.1%（Diamond。選び方の影響で偏っている）。4択なので偶然でも 25%。論文時点の GPT-4（few-shot CoT）は Diamond で 38.8%
  - 採点：4択の正解との照合（回答から「answer is」などを正規表現で取り出して比べる）。LLM による採点は使わない

- 気づき・疑問：
  - GPQA は「採点を簡単にする（4択で照合）」代わりに、「問題を作って検証する」ことに大きなコストをかけている。今日の評価セットは逆で、作るのは軽いが、自由記述の回答を判定するために基準（rubric）と人のラベルが必要になる。どこにコストをかけるかが違う
  - GPQA は「専門家が正解できる＝問題が客観的に正しい」ことを2人の専門家で確かめ、それでも約 74% しか客観性を保証できていない（明らかな専門家のミスを除いた推定）。今日の「分かりやすさ」のような主観的な基準で人と LLM が割れるのは当然だと思えた
  - Hugging Face のデータセットページの Leaderboard（2026年11月時点の表示）では、Diamond の上位モデルは約 91〜94 点だった。論文時点の GPT-4（38.8%）から大きく伸び、検証した専門家の正答率（81.3%）も上回っている。論文では専門家の客観性は約 74% と推定されており、問題1の解説のような誤りも残るので、残り数%の差が「モデルの限界」なのか「問題側の誤り・曖昧さ」なのか区別しにくい。ベンチマークが飽和に近づいている（ただし Leaderboard には提供元の自己申告の値も混ざっている）
  - 3問とも分野が違い、自分が解けそうなのは化学の1問だけだった。「博士レベル」といっても、難しさの種類（公式の発想、専門知識の暗記、多段の推論）は問題ごとに違う。1つの正答率にまとめると、その違いが見えなくなる
  - 疑問：4択はモデルが選択肢から逆算したり、当て推量で 25% 取れたりする。正答率が高いモデル同士の差は、この方法でどこまで信頼できるのか
