- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/config.py` の `RAG_TOP_K` を `5` → `2` に変更した（1か所のみ）。
  - `search_materials` が1回の検索で返すページ数が5件から2件に減る。
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - 質問：「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」
  - モデル：gemini-3.5-flash-lite（変更前後とも同じ）
  - 対象資料：第1〜3回の本講義214ページ（同梱の index.sqlite3）、通常モード（ベクトル検索）
  - 実行コマンド：`uv run python -m app.agent --trace "$Q"`（変更前後とも1回ずつ実行）
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

| | RAG_TOP_K = 5（変更前） | RAG_TOP_K = 2（変更後） |
|---|---|---|
| ツール呼び出し | `search_materials({'query': 'LoRA QLoRA 固定 学習'})` 1回 | 同じ検索語で1回 |
| 回答 | 元の重みは固定し、低ランクの小さな行列の積で表す変化分だけを学習。QLoRAは元の重みを4bitに圧縮する要素を加える | 内容は同じ（「何を固定／何を学習／何を加える」と項目を分けた書き方に変化） |
| 引用根拠 | 第2回・PDF p.51, p.52 | 第2回・PDF p.51, p.52 |
| 時間 | 3.71 秒 | 2.85 秒 |
| 入力／出力トークン | 3,027 / 166 | 1,740 / 195 |
| モデル応答回数 | 2 回 | 2 回 |
| 生成API推定費用 | $0.001323 | $0.001010 |

  - 検索結果の1位はどちらも `lec02-main-p052` で、答えを支えるページは上位2件に入っていた。

- 改善した例と、残る失敗・制約：
  - この質問では、根拠と回答の正しさを保ったまま入力トークンが約43%、費用が約24%減り、時間も短くなった。上位3〜5件は回答に使われておらず、余分な情報だったといえる。
  - 制約：各条件1回の実行で、時間やトークン数のばらつきは確認していない。また、答えが1〜2ページにまとまる質問だったため効果が出やすかった。章をまたぐ質問や、根拠が3ページ以上に分かれる質問では、2件では根拠が足りなくなる可能性がある（今回は未検証）。
- 気づき・疑問：
  - 検索件数を減らしても、モデルが追加検索をして補う動きは見られなかった（呼び出しは1回のまま）。件数を減らしすぎて根拠が足りないとき、モデルが自分で検索をやり直すのか、足りないまま答えてしまうのかが気になる。
  - 出力トークンはむしろ増えていたので、費用の差はほぼ入力側（渡す本文の量）で決まっている。
